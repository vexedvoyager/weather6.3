## A. Open-position gauges on the dashboard (display only) — unchanged from the 2026-11-15 plan

One needle gauge per open position in the dashboard's "Open positions" section, showing how the market's view of each wager has changed since purchase.

### What each gauge shows
- Needle: market's current chance YOUR side wins = current midpoint price of your side (for NO positions, 100 minus the YES price).
- Gray tick: your purchase price (`entry_price_cents`, already stored on each trade).
- Arc between tick and needle: green if the market moved in your favor, red if against.
- Below the gauge: change in points since purchase, and "Sell now for X¢" using the bid (the conservative cash-out value) with per-contract gain/loss.

### Explicitly out of scope
- No price history or intraday trend line. Each run only compares current price to purchase price.
- Model probability is not used for the needle (it does not update intraday; Forecast Refresh skips same-day markets).

### Display-only: must not touch the model or trading
- The gauge prices are never read by forecasting, probability, edge, guard, sizing, or settlement code. The feature only writes two display columns and draws the dashboard.
- The price-saving step in Price Check runs AFTER all trading logic, wrapped in its own try/except, so a failure there logs a warning and can never block trades, settlement, or alerts.
- The dashboard gauge rendering likewise falls back to the existing plain row if anything is missing.

### Implementation outline (~30 min)
1. `trades` table: add columns for the latest bid and ask of the position's side (overwritten every run; additive db migration, existing columns untouched).
2. `src/price_check.py`: after trading logic, write the current bid/ask onto every open trade's row (Price Check already fetches these prices), isolated in try/except.
3. `src/generate_dashboard.py`: render the gauge per open position as inline SVG (no new dependencies). Dashboard already regenerates at the end of every 5-minute Price Check run.
4. Tests: NO-side price conversion, missing/empty bid or ask, gauge color direction, and a test that a failure in the price-saving step does not stop the run.

### Caveats
- Late-day markets can have wide bid/ask spreads; the midpoint can overstate value, which is why the bid is shown underneath.
- A high reading (e.g. 92%) is the market's estimate, not a guarantee.

## C. Block YES bets on above/below markets (strategy change)

**Evidence:** 0 for 5 in real trades (−$26.41) and 0 for 5 in simulation. **All five were New York "high < X" bets** (Oct 22, Oct 26, Nov 2, Nov 14, Nov 15). The cause: NY highs land about 0.7°F above the model's median on average, so the model overrates "below X" when X is near the median (it said about 30%, and these happened 8% of the time). Without these five, NY is +$32.70 instead of +$6.29. Small sample, but it repeats the long-shot pattern from v4/v6.1.1 and rarely triggers, so the cost of blocking is low.

**Scope:** YES only, on threshold markets (Kalshi `strike_type` of greater/greater_or_equal/less/less_or_equal; tickers ending `-T<number>`). NO bets on threshold markets and all bracket (`-B`) bets are unaffected.

**Implementation:**
1. `src/guards.py`: add default `"allow_yes_on_threshold": False` and
   `blocks_yes_threshold(side, ticker, guards) -> bool`, which returns True when side is yes, the ticker's last segment starts with `T`, and the setting is False. Document the evidence in the module docstring next to `min_yes_price_cents`.
2. `src/price_check.py` (~line 234): directly after the `blocks_cheap_yes` check, `if guards_mod.blocks_yes_threshold(want_side, ticker, guards): logger.info("SKIP YES on threshold ticker=%s", ticker); continue`. Skipped, not shadow-tracked (the scorecard already records the market).
3. `config.yaml` `guards:` section: add `allow_yes_on_threshold: false` with a one-line comment.
4. Tests (`tests/test_v64_guards.py`): YES on `-T46` blocked; NO on `-T46` allowed; YES on `-B64.5` allowed; setting `true` disables the block; missing config key falls back to the default.

## Watch list (no code; check at each weekly review)

- **New York — the strongest city, not yet proven.** Most accurate forecasts (typical miss 0.85°F, tied with LA), model beats the market in both valid versions, with the gain coming from NO on "shoulder" brackets 2–5°F from the median. But it's only 13 days (model better on 7) and statistically weak; confirming it needs about 80+ NY days (~3 months). Keep the current size and don't scale up.
- **NY warm bias (+0.7°F).** If it holds for another few weeks (~30 NY days), consider a small NY-specific median shift. Not before: today it would be fitting the model to 13 days.
- **Station hypothesis.** NY (Central Park) and LA (LAX) both settle on stations that general weather apps don't show as "the city." The model may beat traders using generic city forecasts there. Test: check whether other cities with unusual settlement stations show the same pattern as data accumulates.
- **Chicago:** lost in v6.1.1 simulation, flat in v6.3. Keep trading, but move it to shadow if it trails again over the next 30 city-days.
- **Shadow cities:** none look promising. Houston was profitable in both simulated versions but its forecasts trail the market both times (likely luck). Denver beat the market in v6.3 only. Dallas and Seattle are clearly worst. Leave all in shadow.
- **What not to filter:** edge size (40+ point edges looked bad in real trades but matched market prices in simulation), all-threshold markets, and NO price ranges. These patterns flip between versions.
